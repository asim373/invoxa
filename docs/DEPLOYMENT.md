# Production deployment and integration runbook

This runbook documents the supported single-host Docker Compose deployment. It does not assume a
cloud provider. A trusted reverse proxy or hosting platform terminates HTTPS; PostgreSQL, Redis,
the API, and the web container remain private to the host or private container network.

## Supported runtime and environment modes

`APP_ENVIRONMENT` accepts exactly `development`, `test`, `staging`, or `production` (case-insensitive).
Production and staging use the same security validation: non-default authentication secret,
non-local PostgreSQL/Redis, explicit HTTPS public origins, secure CORS/trusted-host configuration,
rate limiting, and configured SMTP delivery. Unknown or misspelled values stop startup. The API and
worker receive the same environment mode; `APP_COMPONENT` is set by Compose so worker-only
processes do not require API-only CORS or SMTP settings.

Development may use the local defaults in `.env.example`. Never use those values in staging or
production. Keep `.env.production` untracked and store credentials using the deployment platform's
secret facility. Do not put secrets in image build arguments, frontend variables, source control,
logs, or support tickets.

## Required production configuration

Copy `.env.example` to an ignored `.env.production` and configure at least:

```dotenv
APP_ENVIRONMENT=production
INVOXA_API_IMAGE=registry.example.com/invoxa/api:<reviewed-release-tag>
POSTGRES_PASSWORD=<unique-secret>
DATABASE_URL=postgresql://<user>:<password>@postgres:5432/<database>
REDIS_URL=redis://redis:6379/0
AUTH_SECRET_KEY=<random-secret-with-at-least-32-characters>
RATE_LIMIT_ENABLED=true
VITE_API_BASE_URL=https://api.example.com
VITE_PUBLIC_APP_URL=https://app.example.com
FRONTEND_BASE_URL=https://app.example.com
CORS_ORIGINS=["https://app.example.com"]
ALLOWED_HOSTS=["api.example.com"]
SAML_PUBLIC_BASE_URL=https://api.example.com
SCIM_PUBLIC_BASE_URL=https://api.example.com
SMTP_HOST=<smtp-host>
SMTP_PORT=587
SMTP_USERNAME=<smtp-user-if-required>
SMTP_PASSWORD=<smtp-secret-if-required>
SMTP_FROM_ADDRESS=no-reply@example.com
SMTP_STARTTLS=true
SMTP_USE_SSL=false
```

`APP_ENVIRONMENT=staging` applies the same requirements. `SAML_PUBLIC_BASE_URL` and
`SCIM_PUBLIC_BASE_URL` are trusted HTTPS **origins** (no path, query, or fragment); endpoint paths
are generated by the application. Localhost, loopback, wildcard CORS/trusted hosts, HTTP public
URLs, default/short auth secrets, local database/Redis URLs, and disabled rate limiting are rejected
for the API. SMTP must select exactly one encrypted transport (STARTTLS or implicit SSL), provide
a sender address, and configure username/password together when authentication is used. Production
and staging never fall back to the development email outbox.

`VITE_API_BASE_URL` is public and compiled into the web bundle. A production build fails unless it
is explicit HTTPS and non-local; rebuild the web image when it changes. `VITE_PUBLIC_APP_URL` may
be set to the public frontend URL and otherwise defaults to the browser origin. Never place a
secret in a `VITE_*` variable.

The base local Compose file explicitly builds web assets with `VITE_BUILD_MODE=development`, which
permits its loopback Docker API URL for local use only. The production Compose overlay forces
`VITE_BUILD_MODE=production`; it retains the trusted HTTPS validation above. Never combine the
production build mode with a localhost or HTTP public API URL.

## Public URLs, proxy, and TLS

Configure DNS and valid public TLS certificates before enabling SAML or SCIM. Route the frontend
hostname to the web container and the API hostname to the API container. Redirect public HTTP to
HTTPS, preserve the configured `Host` header for trusted-host enforcement, and apply bounded body
size and upload timeouts at the proxy. Do not trust arbitrary forwarded-host headers. The SAML and
SCIM resource origins come from explicit server-side settings rather than request headers.

The API is bound to loopback by the production Compose overlay. PostgreSQL and Redis ports are not
published in that overlay. Keep the proxy-to-API path private. The API emits HSTS in staging and
production; the proxy remains responsible for TLS termination and HTTP-to-HTTPS redirection.

The web NGINX configuration logs request paths without query strings and sends `Referrer-Policy:
no-referrer`; preserve this behavior for authentication callbacks. Do not enable proxy logging of
authorization headers, cookies, or query parameters. The SAML SPA handoff uses a short-lived,
single-use code in the URL fragment, not an access token.

## SAML and SCIM prerequisites

SAML remains configured per organization by an authorized owner. Before enabling it, provision the
IdP entity ID, HTTPS SSO URL, and currently valid signing certificate(s) through the existing
organization SAML management path. IdP email mapping must resolve an existing active Invoxa account
and active organization membership; this deployment does not enable JIT. The service provider
Entity ID and ACS are derived from `SAML_PUBLIC_BASE_URL`. If signed AuthnRequests are configured,
mount the SP private key and certificate as protected runtime files and set their paths; never bake
private keys into the image.

SCIM remains Enterprise-only and organization-scoped. Set `SCIM_PUBLIC_BASE_URL` to the trusted API
origin. An owner enables SCIM and creates/rotates/revokes bearer credentials through the existing
management flow. The raw credential is displayed only at creation/rotation; persist it in the IdP's
secret store, not in source or logs. SCIM is Users-only; Groups, Bulk, sorting, and arbitrary PUT
remain unsupported. This runbook does not claim that Microsoft Entra provisioning has been tested.

## Email and generated links

Set `FRONTEND_BASE_URL` to the browser-visible HTTPS frontend origin. Invitation acceptance and
password-recovery links are built from this setting. Configure a deliverable sender, SMTP host and
port, and exactly one TLS mode. Supply SMTP credentials only when required by the mail provider.
Delivery failures return controlled errors and are not logged with message bodies or links. Use a
disposable SMTP sink for later delivery verification; do not test with customer recipients.

## Images, dependencies, and document processing

Build API, worker, and storage-init from the same `INVOXA_API_IMAGE` identity. Storage-init no
longer depends on a Compose-generated project image name. The current Python runtime dependency
closure is recorded in `apps/api/requirements-runtime.lock`; API and worker use the same image and
lock. Frontend dependencies install with `npm ci` against `apps/web/package-lock.json`.

The reviewed runtime line is Python 3.12 and Node 22. The API image installs Tesseract with English
OCR data and `xmlsec1` for signed SAML processing. Debian/Alpine OS package versions and Python,
Node, and NGINX base image digests are not frozen by this repository: apt security updates and base
image tags remain the reproducibility boundary. At each release cut, operators must resolve and
record approved base-image digests, inspect OS package changes, and rebuild/test from that reviewed
input. PostgreSQL 16 and Redis 7 Compose images are pinned to the currently reviewed image digests.
Dependency upgrades are not performed as part of deployment; update the lock only through reviewed
dependency maintenance and regression testing.

The worker healthcheck performs bounded, non-mutating checks for its OCR executable, PostgreSQL
`SELECT 1`, and Redis `PING`. It does not enqueue a synthetic job. The worker container process
provides liveness; dependency checks provide readiness to participate in the configured pipeline.
The API readiness endpoint checks PostgreSQL and Redis. Uploads persist in the `document_storage`
volume; database records and document files must be backed up consistently.

## Migration and startup procedure

The source migration head for this build is **0035**. Migrations 0031–0035 add email verification,
the transactional email outbox, customer account settings, account deactivation, and permanent
deletion tombstones. Migration 0030 adds organization scope to short-lived one-time SAML frontend
login grants; it does not alter SAML assertion validation or SCIM protocol behavior. Review the
exact migration chain from the deployed revision and test it on a disposable copy before
production.

Use Docker Compose v2.24.4 or newer because the production overlay uses `!override` and `!reset` to
remove public port mappings from API/PostgreSQL/Redis. Validate the resolved configuration before
starting services:

```powershell
docker compose --env-file .env.production `
  -f docker-compose.yml -f docker-compose.production.yml config --quiet
docker compose --env-file .env.production `
  -f docker-compose.yml -f docker-compose.production.yml up -d --build
```

The one-shot `migrate` service runs `alembic upgrade head`; API and worker wait for successful
migration, healthy PostgreSQL/Redis, and storage initialization. A failed migration blocks
dependent services. Never point this process at an unintended database. Inspect the resolved
Compose config and database identity before the first deployment.

## Health, readiness, backup, and rollback

```powershell
docker compose ps
docker compose exec -T api alembic current
docker compose exec -T api python -m apps.api.app.worker_health
```

`GET /health` is API liveness. `GET /health/ready` requires PostgreSQL and Redis. Compose API
healthcheck sends an allowed Host header while connecting to loopback. Worker health checks the
non-destructive dependencies listed above. Also verify web health and a controlled document job
with disposable data before production traffic.

Back up PostgreSQL and `document_storage` together and regularly prove restoration. Redis uses
persistence for queued/in-flight jobs, but the database remains authoritative for durable document
and processing state. Retain the prior API/web image identities and database backup for rollback.
Do not automatically downgrade a production schema after data has been written; restore or apply a
forward repair according to a reviewed recovery plan. Do not use `docker compose down --volumes` for
routine deploys or rollback.

## Operator-owned checks

The deployment operator owns DNS/TLS issuance, proxy routing and request limits, secret injection,
SMTP provider credentials/deliverability, base-image digest review, production backup/restore,
database monitoring, and customer-specific SAML IdP setup. External SAML/SCIM interoperability
evidence is not a substitute for these environment-specific checks. Microsoft Entra provisioning
remains intentionally unverified/deferred.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| API fails at startup | `APP_ENVIRONMENT`, required secret URLs, allowed hosts, CORS, SMTP, and migration logs |
| API healthcheck fails behind trusted hosts | First `ALLOWED_HOSTS` entry and resolved Compose healthcheck command |
| Readiness unavailable | PostgreSQL and Redis connectivity from the API container |
| Migration fails | Current revision, migration logs, DB target identity, backup/recovery plan |
| Worker unhealthy | Worker logs, OCR executable, PostgreSQL, Redis, storage permissions |
| Document remains queued | Worker health/logs, Redis, reconciliation interval, shared storage mount |
| SAML unavailable | `SAML_PUBLIC_BASE_URL`, XMLSec availability, org IdP config/certificate and active membership |
| SCIM URL/location incorrect | `SCIM_PUBLIC_BASE_URL`, trusted public origin, proxy path routing |
| Password/invitation email absent | SMTP host/from/TLS/auth and provider delivery logs; use sink for test |
| Browser calls localhost | Rebuild web with explicit HTTPS `VITE_API_BASE_URL` |
